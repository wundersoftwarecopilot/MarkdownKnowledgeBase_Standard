# ADR-001: Store weighing tickets in SQLite in WAL mode

## Context
Recorded retroactively from Handoff.md on 2026-09-01.
Until v0.4 TareLog wrote one CSV file per lane and day on the weighbridge PC.
The reader and the web UI appended to the same files, and corrections and the day view had to scan them.
TareLog runs on one Linux mini-PC in the weighbridge office with no administrator on site.
The reader writes a reading every few minutes per lane, the web UI writes tickets, and the web UI and the report job read all day.
Tickets are legal-for-trade records ([project/CONSTRAINTS.md](../project/CONSTRAINTS.md), section Regulatory and legal), so a power cut must not lose a committed ticket.

## Problem
Where does TareLog store readings and tickets on the weighbridge PC?

## Decision
Store all data in one SQLite database, `data/tarelog.db`, with `journal_mode=WAL` and `synchronous=FULL`.
Every connection is opened by `src/tarelog/tickets/store.py` with a busy timeout of 5000 ms.
Schema changes are numbered SQL migrations in `migrations/`.

## Alternatives considered
- PostgreSQL on the mini-PC: a server to configure, patch and back up, with nobody on site to do it.
- SQLite with the default rollback journal: a long read blocks the writer, so the day view would stall the reader service.
- Keep the CSV files: no transactions; corrections and queries stay file scans.

## Consequences
- One writer at a time: every write transaction must be short, or other writers fail with `database is locked` after 5 seconds (TS-SQLITE-LOCKED).
- Readers never block the writer and see a consistent snapshot.
- Backups must use the SQLite backup API or the `.backup` command, not a file copy, because recent commits sit in the `-wal` file (DB-TICKETS).
- `synchronous=FULL` costs write speed that a weighbridge does not need and protects committed tickets from power loss.
- A second PC writing tickets would need a new decision.
